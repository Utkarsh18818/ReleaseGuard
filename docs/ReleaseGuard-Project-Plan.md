# ReleaseGuard — complete project and implementation plan

Status: approved project direction; first deterministic core implemented October 15. Created October 12, 2026, IST. Historical planning/readiness sections retain their original dates.

## 1. Product decision

Build **ReleaseGuard: The Agent That Remembers Why Deployments Failed** for WeMakeDevs Graph Hacks. An evidence-backed release agent follows dependencies, remembers failed fixes, creates targeted blockers, and withdraws recommendations when facts change.

Primary entry: Agents That Act on Connected Data. Secondary: Agent Memory and Coordination if persistence and handoff are complete. Company Brain is optional, contingent on completed ownership and provenance workflows. Do not dilute the primary demo to enter more tracks.

The user wants a competitive, polished project with scalable architecture and maintainable code. Winning is an objective, not a promised outcome. Prioritize a reliable end-to-end demonstration over feature count.

## 3. User workflow and boundaries

User: engineering lead reviewing a proposed release in a small software company.

Input: release identifier and question, for example, “Can we release checkout v2.4?”

Output: Ready, Blocked, Insufficient evidence, or Needs reassessment; supporting paths; relevant historical outcomes; unresolved checks; proposed workflow actions.

Ready means the configured checks passed against recorded evidence at a stated time and graph revision. It does not certify production safety. Keep this distinction in the recommendation details.

In scope: synthetic company, service dependencies, releases, changes, ownership, incidents, verification evidence, local blocker tasks, persistent memory, investigator/verifier handoff, recommendation invalidation, bounded blast-radius rehearsal.

Out of scope: production deployments, arbitrary code execution, unrestricted Cypher generated by an LLM, broad enterprise connectors, voice, authentication product, arbitrary document ingestion, general-purpose company chatbot, autonomous code fixes.

## 4. Competitive differentiators

1. **Failed-fix memory:** retrieve attempted fixes and observed outcomes; use relevant experience to change the next plan.
2. **Evidence-dependent recommendations:** explicitly record dependencies of a recommendation; mark it stale when relevant facts change.
3. **Graph-backed actions:** create an owner-assigned blocker from an actual query result, with an evidence trail.
4. **Blast-radius rehearsal:** show structurally reachable impact and assumptions; never present reachability as confirmed failure or causal proof.
5. **Persistent handoff:** a restarted verifier continues from saved evidence and unresolved checks.

## 5. Architecture decision

Use a modular monolith with one durable worker process, not microservices. This provides clear interfaces and independent worker scaling without distributed operational overhead during a four-day event.

Proposed stack, to validate against official documentation when implementation begins:

- Python 3.12, FastAPI, Pydantic, pytest; async HTTP orchestration.
- Official FalkorDB Python client; use an adapter and bounded thread pool if client calls are synchronous.
- React + TypeScript + Vite; a proven graph visualization library chosen after checking maintenance and API documentation.
- One LLM provider behind an adapter; model selected using tool-call reliability, cost, and latency. Never require a specific commercial model to replay deterministic evaluations.
- Docker Compose: API, worker, FalkorDB, frontend, and operational Redis if required.
- Operational Redis queue with durable consumer acknowledgements and retry support. Use a maintained queue library whose delivery semantics are verified; do not invent queue infrastructure.

FalkorDB owns domain relationships, source facts, task state, investigations, memory, and recommendation provenance. The queue owns delivery and leases, not decision truth. Evidence fixture files are immutable inputs, not an alternative reasoning database.

Architecture:

```text
React UI -> FastAPI -> Application services -> Domain policy / graph ports
                         |                        |
                         v                        v
                    Job dispatcher           FalkorDB adapter
                         |                        |
                         v                        v
                    Durable queue       Tenant graph / provenance / memory
                         |
                         v
                    Worker -> Investigator -> Verifier -> Policy gate
                                |                 |
                                +-- bounded graph tools --+
                                +-- model provider adapter +
```

HTTP handlers validate requests, authorize graph selection, dispatch work, and serialize results. They contain no agent loop or Cypher. Domain policies contain no HTTP, queue, model SDK, or database imports.

## 7. Graph model

Each trusted tenant identifier maps server-side to a graph name. Never accept an arbitrary graph name from a client. The hackathon UI can use one configured synthetic tenant. Enforce this boundary in the adapter; do not claim production multi-tenancy without validation.

All domain nodes: stable `id`, `created_at`, `updated_at`, `revision`, and source linkage where applicable. Imported relationship facts: stable fact identifier, provenance, observed time, validity interval when relevant, and active/superseded status. Index identifiers and frequent lookup fields using supported FalkorDB capabilities.

| Node | Key properties | Relationships |
|---|---|---|
| Service | id, name, criticality | DEPENDS_ON Service; OWNED_BY Team |
| Team / Person | id, display_name | MEMBER_OF Team; REVIEWER_FOR Service |
| Release | id, version, proposed_at | HAS_CHANGE Change |
| Change | id, summary, risk_tags | TOUCHES Service; SUPPORTED_BY Source |
| Incident | id, severity, status, occurred_at | AFFECTED Service; HAD_ATTEMPT Attempt |
| Attempt | id, technique, observed_outcome | RESULTED_IN Outcome; SUPPORTED_BY Source |
| Procedure | id, version, description | APPLIES_TO Service; DERIVED_FROM Outcome |
| Verification | id, check_type, result, expires_at | VERIFIES Change/Service; SUPPORTED_BY Source |
| Source | id, fixture_uri, checksum, observed_at | provenance anchor |
| Investigation | id, state, graph_revision, budget | FOR_RELEASE Release; HAS_FINDING Finding |
| Finding | id, kind, statement, status | USES_EVIDENCE EvidenceUse |
| EvidenceUse | fact_id, fact_revision, path_snapshot | REFERS_TO Source/Fact |
| Recommendation | id, status, assessed_revision | FOR_RELEASE Release; DEPENDS_ON_FACT Fact |
| Task | id, state, idempotency_key | BLOCKS Release; ASSIGNED_TO Team/Person; JUSTIFIED_BY Finding |
| Episode / Handoff | id, state, completed_steps, pending_checks | FOR_INVESTIGATION Investigation |

Represent recommendation-critical relationships as addressable Fact nodes alongside traversal edges if direct edge identifiers/versioning are insufficient. Select one consistent implementation after verifying supported query behavior. Avoid an overloaded schema where every relationship is converted into a node without a query need.

Dependency direction: `A DEPENDS_ON B` means failure of B may affect A. Upstream consumer traversal follows incoming DEPENDS_ON edges. Changed-service downstream dependencies follow outgoing edges. Test direction explicitly.

## 8. Pipelines and contracts

### P1 — Idempotent ingestion

Fixture manifest -> schema validation -> stable-ID normalization -> provenance creation -> upsert facts -> supersede changed facts -> graph revision increment -> invalidation scheduling.

- Reject broken references and unsupported relationship types.
- Record source checksum and import ID. Same input replay creates no duplicates or unnecessary revision changes.
- Preserve historical outcomes; do not overwrite failed attempts with the later successful result.
- Serialize mutations per tenant for the MVP. Verify transaction guarantees before assuming multi-query atomicity.
- Domain mutation and revision change must be committed together where supported. A persisted outbox/durable pending marker and recovery scan close the mutation-to-queue gap. No silent lost invalidations.

### P2 — Release assessment

API request -> persist investigation + job -> acquire lease -> capture graph revision -> resolve changed services -> bounded dependency traversal -> retrieve relevant incidents and verification -> retrieve historical attempts -> investigator findings -> verifier recheck -> deterministic policy -> persist recommendation/evidence -> publish UI event.

- Tool calls select allowlisted query templates with validated parameters.
- Limit traversal depth, returned rows, model calls, retries, elapsed time, and token budget.
- Graph tools return typed IDs, paths, source records, revision, and explicit truncation indicators.
- Investigator proposes findings. Verifier checks referenced IDs, active fact revisions, unresolved blockers, and missing required evidence.
- Final state comes from deterministic policy. Model prose cannot override a failed mandatory check.
- If graph revision changes during assessment, revalidate relevant dependencies before publishing. Retry once or publish Needs reassessment; never publish an unchecked old result as current.

### P3 — Workflow action

Validated finding -> proposed task -> policy check -> unique action key -> create Task and evidence links -> persist action outcome -> display action.

The automated action is a task in the synthetic release workflow. Replaying a job must not duplicate tasks. Enforce idempotency under concurrency using a verified uniqueness/atomicity mechanism or serialized tenant writes. Do not rely on a read-then-write check alone.

### P4 — Failed-fix memory and handoff

Observed attempt/outcome -> source validation -> persist episode + semantic links -> optional reviewed procedure -> retrieve by affected service and relevant conditions -> structured handoff.

Handoff includes investigation ID, graph revision, validated findings, completed steps, pending checks, action IDs, and budget remaining. A second agent rereads persisted state rather than trusting a prose summary. Historic similarity suggests relevance, not guaranteed causality.

### P5 — Recommendation invalidation

Fact mutation -> durable mutation event -> identify affected recommendations -> mark Needs reassessment -> enqueue bounded reassessment -> verify updated evidence -> publish replacement recommendation linked to previous version.

Track both used facts and query scope. A newly inserted incident or dependency was not in the old evidence set, so exact fact dependencies alone cannot catch it. Maintain watched service IDs and relation classes; expand new dependency impact or conservatively invalidate relevant releases. If completeness is uncertain, invalidate all active recommendations in the tenant.

Expose the previous verdict with its timestamp and stale state immediately; background reassessment must not leave a misleading Ready badge.

### P6 — Blast-radius rehearsal

User selects hypothetical failed service or feature flag -> validate scenario -> read graph snapshot -> bounded incoming dependency traversal -> apply explicitly modeled flag/dependency conditions -> return reachable consumers and paths -> compare scenarios.

Read-only hypotheses must not modify the canonical graph. State assumptions, depth limits, and truncation. Do not infer outage probabilities from uncalibrated model confidence.

## 9. State and API contracts

Investigation states: queued -> running -> verifying -> completed; terminal failed/cancelled. Recovered jobs resume from persisted checkpoints. Failed verification is a business result; infrastructure failure is a failed job.

Recommendation states: Ready, Blocked, Insufficient evidence, Needs reassessment. Preserve versions; never silently replace history.

Suggested endpoints:

- `POST /releases/{id}/assessments` with idempotency key; returns investigation ID.
- `GET /investigations/{id}` for canonical state and progress.
- `GET /investigations/{id}/events` for server-sent updates; polling fallback.
- `GET /releases/{id}/recommendations/latest` includes stale state and assessed revision.
- `GET /findings/{id}/evidence` returns bounded paths and sources.
- `POST /tasks/{id}/resolve` validates required verification evidence.
- `POST /rehearsals` accepts a bounded hypothetical scenario.
- Demo-only fixture events under a separately configured administrative route.

Errors: stable code, human-readable message, correlation ID, retryable flag. Never expose raw credentials or stack traces to users.

## 10. Policy, reliability, and scalability

Mandatory checks are configured per fixture release: valid ownership, applicable passing verification, no unresolved release blocker, and current evidence. Missing dependency coverage produces Insufficient evidence. Known violations produce Blocked. Relevant concurrent change produces Needs reassessment.

- Bounded workers; parallel reads where safe; serialized writes per tenant initially.
- At-least-once delivery with idempotent effects. Acknowledge only after persisted completion.
- Retry transient network/provider failures with capped exponential backoff and jitter; do not retry validation errors.
- Failed jobs retain stage and error context; expose retry without losing evidence.
- FalkorDB persistence volume and backups; verify restart persistence in the demo environment.
- Model unavailable: show graph findings and incomplete assessment, not a fabricated completed agent run.
- Graph unavailable: fail the core investigation visibly. No hidden fixture answer fallback.
- Revision-keyed caches only; cache entries never override evidence freshness.
- Bound graph size, path depth, pagination, request size, and streaming duration.
- Scale API replicas separately from workers; keep canonical state outside process memory.
- Later: partition tenant workers, enforce graph isolation, read/write load tests, durable outbox guarantees, retention, auth, and finer invalidation. These are roadmap items, not completed claims.

No premature Kubernetes, distributed multi-service orchestration, or custom event bus. Scalability comes from contracts, durable state, bounded workloads, and measured bottlenecks.

## 13. Synthetic dataset and evaluation

Company A: around 10 services, 3 teams, several synthetic reviewers, 3 historical incidents, 2 releases, checks, procedures, and source records. Include cycles, an irrelevant incident, expired verification, failed retries, and a new dependency added after assessment.

Freeze an evaluation set before tuning prompts. Keep expected answers inaccessible to the agent. Cases cover:

1. Simple service ownership.
2. Three-hop consumer impact with exact expected service IDs.
3. Cycle handling and traversal truncation.
4. Relevant failed-fix retrieval versus irrelevant history.
5. Missing/expired verification -> Insufficient evidence.
6. Unresolved blocker -> Blocked.
7. New incident -> immediate stale marking.
8. New dependency -> stale marking even without an old fact reference.
9. Mutation during assessment -> no fresh-looking stale verdict.
10. Worker restart -> persisted handoff continues.
11. Duplicate job -> one task.
12. Graph loss -> explicit failure, no canned result.

Compare same model, same sources, comparable budgets: ordinary document retrieval versus graph tools. Include easy and relationship-heavy questions. This is a small controlled demo benchmark, not a universal claim against vector retrieval.

Metrics: impacted-service precision/recall; source-supported finding rate; verdict correctness; stale-result detection; persistence success; duplicate tasks; median and p95 assessment/query latency; model cost per assessment. Separate deterministic graph correctness from model variability. Record hardware, graph size, query bounds, repetitions, and failures.

Targets: all deterministic safety/state cases pass; no duplicate tasks in retry tests; every factual finding cites valid evidence; no knowingly stale Ready result. Latency targets are provisional until measured; avoid invented performance numbers.
